# 从 KVzip 分块评分到边缘 LLM 请求调度与 KV 缓存协同

**学习日期：2026 年 11 月 11 日**  
**学习主题：KVzip 的工程化评分机制，以及边缘 LLM 服务中的请求调度与缓存协同问题**

## 一、KVzip 为什么需要 Chunked Scoring？

前面已经理解了 KVzip 的核心思路：模型不预先猜测用户未来会提出什么问题，而是通过上下文重建（Context Reconstruction），观察重建过程中的 Query 对历史 KV 的注意力，再据此评估历史 KV 的重要性。

但当原始上下文非常长时，直接执行完整的重建评分会遇到工程问题。假设原文有 100K Token，如果把整段上下文作为重建输入，那么每个重建 Query 都可能需要与大量历史 Key 计算注意力。若显式构造完整评分矩阵，其元素规模会随上下文长度平方增长。

为降低单次评分的矩阵规模，KVzip 使用 **Chunked Scoring（分块评分）**：把长上下文切分成若干块，逐块完成评分，最后再将各块的分数按照原始 Token 位置合并。

### 1.1 用 20K Token 的上下文举例

假设原始上下文长度为：

\[
n_c=20K
\]

每个 Chunk 的长度为：

\[
m=2K
\]

那么总共需要处理：

\[
T=\frac{n_c}{m}=\frac{20K}{2K}=10
\]

也就是将原文划分为 10 个 Chunk：

\[
C_1=[t_1,t_2,\ldots,t_{2000}]
\]

\[
C_2=[t_{2001},t_{2002},\ldots,t_{4000}]
\]

依此类推，直到 \(C_{10}\)。

### 1.2 第一个 Chunk 如何评分？

对于第一个 Chunk，构造重建输入：

```text
Repeat the previous context:

[t1, t2, ..., t2000]
```

随后利用此前 Prefill 建立的原始 KV Cache，执行一次前向计算。当前重建输入会产生 Query、Key 和 Value；其中 Query 用于查询历史缓存，当前输入产生的 Key 也会参与 Attention 的归一化。

### 1.3 第二个 Chunk 为什么要带上前一块末尾的 8 个 Token？

处理第二个 Chunk 时，不能简单地把它当成完全独立的新文本。按照本次学习中采用的示例，重建输入会带上前一个 Chunk 末尾的 8 个 Token，为当前 Chunk 提供局部衔接信息：

```text
Repeat the previous context starting with:

[前一个 Chunk 最后的 8 个 Token]

[当前 Chunk 的 2000 个 Token]
```

这样做的直观目的，是避免当前 Chunk 完全脱离前文局部语境。这里的 8 个 Token 是本次理解所用的示例设置，不能据此推断所有实现或所有模型都必须使用相同长度。

为便于说明，假设本次重建输入总长度为 2008 个位置：

\[
n_{\mathrm{in}}=2008
\]

当前需要评分的原始缓存 Key 有 2000 个；当前重建输入自身产生 2008 个 Key。于是，在这个简化设置下，参与计算的 Key 数量为：

\[
2000+2008=4008
\]

Attention 评分矩阵的形状为：

\[
\boxed{2008\times4008}
\]

这里的 2008 行对应当前重建输入的 Query 位置，4008 列对应两类 Key：

- 前 2000 列：当前 Chunk 对应的原始历史缓存 Key，是最终需要评分的对象。
- 后 2008 列：当前重建输入自身产生的 Key，参与 Attention 的 Softmax 归一化，但不作为原始历史 KV 的淘汰评分对象。

需要特别注意因果注意力掩码：对于某个 Query 位置，只有按照因果规则允许访问的 Key 才真正参与该行的 Softmax；尚不可访问的后续位置会被 Mask。

### 1.4 为什么计算时要包含当前输入 Key，最终却只取前 2000 列？

这是 Chunked Scoring 中容易混淆的细节。

Softmax 的分母应该包含当前 Query 能够访问的全部 Key。当前重建输入产生的 Key 虽然不是最终要评估的历史缓存对象，但它们也属于 Attention 的竞争范围。如果只拿历史缓存 Key 计算 Softmax，就相当于把当前输入 Key 从分母中删掉，历史缓存 Key 的注意力权重会被重新归一化，数值可能被人为放大。

因此正确顺序是：

1. 历史缓存 Key 与当前输入 Key 一起参与 Attention 计算，并遵守因果 Mask。
2. 完成 Softmax 后，只提取原始历史缓存 Key 对应的前 2000 列。
3. 对每个历史 KV，沿重建 Query 位置（以及对应的 Query Head 维度）取最大注意力，得到重要性评分。

可以概括为：

\[
A=\operatorname{Softmax}\left(\frac{QK_{\mathrm{all}}^\top}{\sqrt d}+M\right)
\]

其中 \(M\) 表示因果 Mask。随后只取历史缓存 Key 对应的列：

\[
\bar A=A[:,0:2000]
\]

再对每个历史 Key 的列做最大值聚合：

\[
S_j=\max_i\bar A[i,j]
\]

若考虑多个对应的 Query Head，则还需要在相应 Head 维度上进行最大值聚合。

**核心区别：全部可访问 Key 参与 Softmax 竞争，但只有原始历史缓存 Key 进入最终重要性评分。**

### 1.5 汇总所有 Chunk 的评分

每个 Chunk 都会得到一组与其原始位置对应的评分。例如：

\[
S_1=[s_1,\ldots,s_{2000}]
\]

\[
S_2=[s_{2001},\ldots,s_{4000}]
\]

一直到：

\[
S_{10}=[s_{18001},\ldots,s_{20000}]
\]

最后按原始 Token 顺序拼接：

\[
\boxed{S=[S_1,S_2,\ldots,S_{10}]}
\]

这一步不是每个 Chunk 独立决定最终保留比例，而是先得到完整的 Token 重要性评分，再根据整体缓存预算进行筛选。

### 1.6 分块评分的复杂度直觉

若直接对长度为 \(n_c\) 的上下文构造完整评分矩阵，其元素规模可粗略表示为：

\[
O(n_c^2)
\]

若每块长度为 \(m\)，则单块评分矩阵规模约为：

\[
O(m^2)
\]

总块数约为 \(n_c/m\)，因此所有分块的评分矩阵元素规模合计约为：

\[
\frac{n_c}{m}\cdot O(m^2)=\boxed{O(mn_c)}
\]

单次评分矩阵的峰值规模约为：

\[
\boxed{O(m^2)}
\]

当 Chunk 长度 \(m\) 固定时，单次评分矩阵的规模不会随着完整上下文长度平方增长。

这里讨论的是**评分矩阵规模的复杂度直觉**，不是整个模型前向计算所有 FLOPs 的完整复杂度，也不应忽略 FlashAttention 等实现可能采用分块计算而不显式保存完整注意力矩阵。实际实现还会受到 Prompt 长度、局部重叠长度、Head 数量和具体注意力内核等因素影响。

## 二、KVzip 的两种评分与部署模式

KVzip 使用上下文重建评估 KV 重要性，但评分结果可以采用两种不同粒度。

### 2.1 Context-dependent：上下文相关评分

Context-dependent 针对当前具体文档进行评分。假设边缘服务器需要处理一份 100K Token 的网络安全分析报告，其中包含攻击入口、漏洞编号、受影响主机、攻击过程和防御措施。

模型对这份报告执行上下文重建，再针对各层、各 KV Head 中的历史 KV 计算重要性分数。下面是一个教学示例：

| 历史 KV 内容 | 重建评分 | 示例决策 |
|---|---:|---|
| 攻击入口 | 0.90 | 保留 |
| 漏洞编号 | 0.85 | 保留 |
| 一般背景信息 | 0.10 | 淘汰 |
| 受影响主机 | 0.95 | 保留 |
| 防御措施 | 0.80 | 保留 |

> 注：表中评分为教学示例，不是论文实测数据。

这种方式的特点是：

1. 评分对象是当前文档中的具体 KV。
2. 能区分同一文档中不同 Token 的重要性。
3. 压缩结果能够适应当前文档的内容。
4. 每遇到新的 Context，通常都需要额外执行相应的评分过程。

因此，它的优势是细粒度和上下文适应性，代价是每份新文档都要承担额外评分开销。

### 2.2 Context-independent：上下文无关的静态 Head 评分

如果边缘平台需要处理大量不同文档，为每篇文档都执行一次上下文重建评分，成本可能较高。Context-independent 的思路是：先使用代表性上下文，对模型不同层、不同 KV Head 的整体重要性进行离线统计，形成模型级的静态 Head 评分。

按照当前阅读记录，论文使用约 88K Token 的英文书籍样本进行代表性评分。得到 Token 级分数后，再沿序列维度聚合为 Head 级分数：

\[
S\in\mathbb R^{L\times H\times n_c}
\]

\[
\boxed{
S_{\mathrm{head}}(\ell,h)=\max_{i=1,\ldots,n_c}S(\ell,h,i)
}
\]

其中：

- \(\ell\)：模型层编号；
- \(h\)：KV Head 编号；
- \(i\)：上下文中的 Token 位置。

经过聚合后，评分不再区分某篇具体文档里的每一个 Token，而是描述模型中某个 Head 在代表性样本上表现出的整体重要性。新文档到来时，可以复用这份静态 Head 配置，减少逐文档评分的开销。

这种方式更容易部署，但粒度也更粗：它无法像 Context-dependent 一样，针对每篇文档识别具体哪些 Token 更重要。代表性样本能否覆盖实际部署中的文档分布，也会影响静态评分的适用性。

### 2.3 两种模式的取舍

| 对比维度 | Context-dependent | Context-independent |
|---|---|---|
| 评分对象 | 当前文档中的具体 KV | 模型层级的 KV Head |
| 评分依据 | 当前文档的重建过程 | 代表性样本的离线统计 |
| 评分粒度 | Token 级 | Head 级 |
| 新文档开销 | 需要额外评分 | 可复用静态配置 |
| 主要优势 | 更细粒度、更适应当前文档 | 部署成本较低、适合批量文档 |
| 主要局限 | 每份文档都要付出评分成本 | 可能无法适应不同文档的细节差异 |

这两种方式体现了一个典型权衡：

\[
\boxed{\text{压缩适应性与精细度}\quad\longleftrightarrow\quad\text{评分和部署成本}}
\]

## 三、对 KVzip 方法的局限性思考

首先，压缩并不是免费的。Context-dependent 需要执行额外的上下文重建前向计算，因而会增加预处理成本。只有当压缩后的缓存能够被后续请求充分复用时，这部分开销才更容易被摊薄。

其次，重建评分是一种基于注意力行为的重要性估计。高分表示某个历史 KV 在重建过程中受到较高关注，但这并不构成“所有未来问题都能被正确回答”的理论保证。低分 KV 也不一定完全没有价值：例如某个只出现一次的 IP 地址、时间戳或漏洞编号，可能恰好是未来某个精确查询的唯一答案。

因此，评价 KVzip 时不能只看压缩率或重建评分，还应结合具体下游任务测试信息保留效果，尤其是精确检索、长上下文问答和结构化信息抽取等场景。

## 四、从 KVzip 延伸出的边缘计算研究想法

KVzip 的重要性评分可以启发边缘侧的缓存管理，但评分本身不能直接决定 KV 一定应该放在 GPU 显存还是 SSD。实际数据放置还需要考虑访问频率、请求时延要求、显存容量、DRAM/SSD 带宽、数据搬运成本和缓存更新频率。

一个可能的研究方向是：把 KV 重要性作为缓存决策的一个输入，与访问热度、数据传输成本和资源状态联合建模。例如，高重要性且高频访问的 KV 可以优先驻留在快速存储层；低频但仍需保留的 KV 可以考虑放在容量更大的存储层。这里属于个人研究设想，并不是 KVzip 原论文已经提出或验证的功能。

## 五、转向边缘系统：请求调度与 KV 缓存为什么需要协同优化？

在完成 KVzip 的学习后，我开始阅读另一篇与边缘计算联系更紧密的论文：

**Co-Optimizing Request Scheduling and KV Caching for Edge LLM Serving**

这篇文章关注的问题从单个模型内部的 KV 压缩，转向多边缘节点上的请求调度与缓存管理。当前阶段先建立系统模型，具体算法和理论部分仍待继续阅读。

### 5.1 一个三节点边缘服务场景

假设边缘节点 A、B、C 都部署了同一个大语言模型。客户端请求由两部分组成：公共系统提示词和知识库前缀 \(P\)，以及当前用户的专属问题 \(Q\)。模型生成回答时需要利用前缀 \(P\) 对应的 KV Cache。

如果目标节点已经缓存了 \(P\) 对应的 KV Block，就可能复用已有缓存，减少重复的前缀计算；如果目标节点没有相应缓存，则需要重新计算这些 KV。与此同时，不同节点的算力、显存占用和请求队列状态并不相同。

因此，选择服务节点时至少要同时考虑以下信息：

1. **请求到达与前缀需求：** 请求什么时候到达，需要使用哪些公共前缀或缓存块。
2. **节点缓存状态：** A、B、C 分别已经保存了哪些 KV Block，是否存在可复用前缀。
3. **节点资源状态：** 各节点的排队情况、GPU 显存、计算能力和当前负载。
4. **未来复用机会：** 当前请求如何影响缓存空间，后续请求是否可能继续使用已有 Block。

### 5.2 为什么请求调度和缓存管理不能完全分开？

假设请求需要使用前缀 \(P\)：

- 节点 A 已经缓存了 \(P\)，但当前队列很长；
- 节点 B 没有缓存 \(P\)，但当前负载较低；
- 节点 C 也缓存了 \(P\)，且队列长度处于中等水平。

如果只考虑缓存命中，可能会优先选择 A；如果只考虑当前负载，可能会选择 B。但 A 的排队等待时间可能抵消缓存命中带来的收益，而 B 虽然空闲，却需要重新计算前缀 KV。C 可能在缓存复用和排队时延之间取得更好的平衡。

因此，节点选择会影响缓存命中和计算开销；缓存放置与淘汰又会改变后续请求可选择的节点及其服务时延。两者存在相互作用，需要放在同一个系统模型中考虑。

> 以上三节点案例是用于理解系统耦合关系的教学推演，不是论文的实验设置或实测结果。

### 5.3 当前形成的系统模型理解

目前可以把该问题初步归纳为：在多个边缘节点上，系统需要根据请求需求、缓存状态和节点资源状态，决定请求由哪个节点处理，以及已有 KV Block 如何复用和管理。

本次记录到这里主要完成了问题场景和关键状态信息的梳理。论文具体采用什么优化目标、有哪些约束、如何设计在线算法，以及理论保证如何推导，仍需要结合论文正文继续核对，暂不在本篇中补写未经确认的细节。

## 六、本次学习形成的理解

本次学习把两个层次的问题联系了起来：

- 在 KVzip 中，重点是判断一份上下文中的哪些历史 KV 值得保留；Chunked Scoring 解决的是长上下文评分时单次矩阵规模过大的工程问题。
- 在边缘 LLM 服务中，问题进一步扩展为多个节点之间如何安排请求、复用缓存和分配有限资源。即使某个节点拥有目标 KV Cache，也不意味着它一定是当前请求的最佳服务节点，因为排队时延和资源状态同样重要。

这让我开始从“如何压缩一份 KV Cache”转向思考“如何在多个边缘节点之间管理和复用 KV Cache”。前者更偏向模型推理内部的缓存表示，后者则涉及边缘系统中的请求调度、缓存放置和资源协同。
