# HARD-KV 学习记录：从三级缓存、温度校准到 GPU 友好的索引规整

> **记录日期：**2026 年 10 月 20 日  
> **学习论文：** *HARD-KV: Head-Adaptive Regularization for Decoding-time KV Compression*  
> **本次内容：**Cascade Cache 后两层、Logits Calibration、System-Aware Index Regularization  
> **记录说明：**本文整理当天的论文阅读和理解，手算与索引示例均为教学假设，不代表本人进行了代码复现或性能实验。

## 一、今天的学习主线

昨天已经初步了解了 HARD-KV 的 Dense Cache：它主要保存近期生成的完整 KV，降低过早丢失局部上下文的风险。今天继续讨论 Sparse Cache 与 Condensed Cache，并进一步学习论文的另外两项关键机制。

在阅读中，我逐渐把问题分成了三个层次：

1. **缓存应该处于什么状态？** 新产生的 KV、动态选择的历史 KV、较老且需要压缩的 KV，管理方式不应该完全相同。
2. **每个 Head 应该保留多少 KV？** Top-p 可以自适应决定数量，但不同算法给出的评分分布未必能够直接比较。
3. **选择结果怎样真正跑得快？** 不同 Head 的索引集合长度不同、位置分散，可能使元数据准备和 GPU 调度抵消一部分稀疏计算收益。

这一思路把论文的三个部分串在一起：**Cascade Cache 管理生命周期，Logits Calibration 统一 Top-p 标尺，Index Regularization 管理系统执行成本。**

## 二、Cascade Cache：第二层 Sparse 与第三层 Condensed

### 2.1 Sparse Cache：用 Top-p 进行动态选择

当历史 token 逐渐离开 Dense 窗口，HARD-KV 允许根据不同 Head 的重要性分布，选择继续参与 Attention 的历史 KV。其直观机制是 Top-p：按概率从高到低排序，选择累计质量达到阈值的最小前缀集合。

**教学示例：**某 Head 对五个历史位置的权重为：

| Token | T1 | T2 | T3 | T4 | T5 |
|---|---:|---:|---:|---:|---:|
| 权重 | 0.50 | 0.25 | 0.15 | 0.07 | 0.03 |

若设置 \(p=0.9\)，则：

\[
0.50+0.25+0.15=0.90
\]

因此，满足阈值的候选是 **T1、T2、T3**。若另一个 Head 的概率更均匀，可能需要保留四个或五个 token 才能达到相同阈值。

由此我理解到：**Top-k 固定保留数量，Top-p 依据注意力质量的集中程度决定数量。**这为 Head-wise 自适应预算创造了条件，但前提是用于 Top-p 的分数需要经过合适的概率校准。

### 2.2 Condensed Cache：为什么还要管理更老的 KV？

仅有 Sparse 选择并不足以保证实际执行效率。假设几个 Head 的选择集合分别为：

```text
Head 1：T1、T3、T7
Head 2：T2、T5、T8、T9
Head 3：T1、T4
```

这些集合从语义选择的角度可能合理，却带来 **长度不同、逻辑索引分散、选择结果随 Decode 改变** 等问题。对于依赖规则索引及较稳定批处理形状的推理框架，动态管理也会产生成本。

Condensed Cache 面向更长期的数据约束，可结合更进一步的缓存压缩与整理。今天记录的相关操作包括：

- **Eviction（淘汰）：**删除不再保留的 KV 信息。
- **Weighted Merging（加权合并）：**在相应策略下，将部分 KV 信息合并为更紧凑的表示。
- **Rewrite（重写）：**把仍要使用的 KV 整理进更规则的物理存储布局。

这里需要区分：**淘汰和合并会改变保留的信息，重写本身主要调整数据布局。**三者不是完全同一种操作，具体执行由系统策略和缓存预算约束决定。

### 2.3 Cautious Update：不要根据一次评分就永久淘汰

今天进一步认识了论文中的 **Cautious Update（谨慎更新）**：某个旧 token 对当前 Query 不重要，不等于它对随后几个 Query 都不重要。

因此，Dense 向 Sparse 的过渡并不是看一次注意力结果便做不可逆删除，而是累积窗口内多个 Query 的选择 Mask；在相关 Block 完整离开 Dense 窗口后，再根据累计选择结果进行压缩决策。对于有硬预算限制的情况，还需根据候选的累计支持程度排序。

我的理解是：**这相当于在决定删除历史证据前，多观察几次它是否被需要。**“累计投票”是帮助理解的类比，并不意味着所有场景都采用固定次数的简单多数表决。

## 三、Logits Calibration：相同的 Top-k 排名，不代表相同的 Top-p 结果

### 3.1 为什么必须校准？

不同 KV 选择算法可能会改变原始 Attention 分数的分布。即便变换前后排名不变，归一化后概率的集中程度也可能不同。

例如下面两组教学数据：

| Token | T1 | T2 | T3 | T4 |
|---|---:|---:|---:|---:|
| 原始分布 | 0.40 | 0.30 | 0.20 | 0.10 |
| 变换后分布 | 0.70 | 0.20 | 0.07 | 0.03 |

两种分布的排名都是 \(T1>T2>T3>T4\)，因此 **Top-2 结果相同**。但当 \(p=0.9\) 时：

- 原始分布需要 T1、T2、T3 三个位置；
- 变换后分布只需 T1、T2 两个位置。

如果变换使概率过度集中，就可能出现 **Selection Collapse（选择塌缩）**：沿用同一个 Top-p 阈值，结果选中的 KV 数量异常减少。

### 3.2 温度缩放改变什么？

温度化 Softmax 可表示为：

\[
P_i(T)=\frac{e^{z_i/T}}{\sum_j e^{z_j/T}},\qquad T>0
\]

其中 \(z_i\) 是待归一化的 Logit。通常：

- \(T<1\)：概率趋于集中；
- \(T>1\)：概率趋于平缓；
- \(T=1\)：得到未经额外温度缩放的 Softmax。

对于同一组固定 Logits，**正温度变化不改变分数排序，但会改变累计概率质量**。因此可以通过调整温度，尽量保留原评分方法的重要性排序，同时减少 Top-p 概率尺度的偏差。

需要注意：不同评分变换 \(g\) 可能要求不同的校准顺序；不能把“先变换再缩放”与“先缩放再变换”无条件视为相同。

### 3.3 如何寻找合适的温度？

作者不是随意设定 \(T\)，而是将其当作待优化参数，比较原始 Attention 与校准分布在相关 Top-k 选择集合上的累计概率质量，使两者尽量接近。

**方法一：梯度下降。**设置初始温度，计算误差，再沿减小误差的方向调整。简化的更新表达式为：

\[
T_{\mathrm{new}}=T_{\mathrm{old}}-\eta\frac{\partial L}{\partial T}
\]

其中 \(L\) 表示校准误差目标，\(\eta\) 为学习率。实际求解需保证温度为正，并使用相应的优化策略。

**方法二：二分搜索。**如果目标累计概率随温度满足可利用的单调关系，可以设置上下界、反复检查中点，逐渐缩小温度区间。这不是对任意变换都无条件适用的搜索法。

对我而言，这部分最重要的收获是：**温度不是为了让所有分数看起来相同，而是让不同评分方案的 Top-p 决策建立在更可比较的概率质量上。**

## 四、System-Aware Index Regularization：选择得少，不一定执行得快

### 4.1 补充概念：CUDA Graph

GPU Decode 包含一系列 Kernel 和依赖操作。若每一步都由 CPU 分别提交多个 GPU Kernel，会产生调度开销。CUDA Graph 可以捕获并复用相对稳定的执行图，减少重复提交成本。

不过，Head-wise Top-p 会造成各 Head 的有效 KV 长度和索引集合动态变化。**这不等于 CUDA Graph 一定失效，而是可能使原有执行图的形状、地址或元数据准备难以直接复用。**

类似地，PagedAttention 通过逻辑 Block 与物理 Block 的映射管理 KV；动态 Head-wise 选择也可能增加 Block Table、选择 Mask 和不同层索引的准备成本。这里的挑战是元数据与物理布局适配，而不是 Top-p 本身必然破坏物理 Block。

### 4.2 Rewrite Cache：先整理，再高效执行

假设 Head 1 想使用 T1、T4、T9。Rewrite 可以把这些有效 KV 整理到连续或规则的物理位置，便于后续执行。

```text
原布局：T1  T2  T3  T4  T5  T6  T7  T8  T9
选中：  ✓           ✓                   ✓
重写：  T1  T4  T9
```

优势是后续读取更规则；代价是额外的数据读取、复制和写入。是否值得 Rewrite，取决于整理一次的开销能否被后续 Decode 的收益抵消。

### 4.3 Sparse Loading：保留布局，利用 Mask 选择

不立即搬动 KV，而是通过选择 Mask 告诉执行过程哪些位置有效：

```text
Token：T1 T2 T3 T4 T5 T6 T7 T8 T9 T10
Head1： 1  0  0  1  0  0  0  0  1  0
```

优点是省去或减少数据重写；但不同执行后端可能仍要承担掩码、索引准备及冗余访问成本。

### 4.4 Flatten Index：让不同长度索引更易组织

例如：

```text
H1：10 23 48
H2：10 77 63 90
H3：10 54
```

为了说明统一形状的思路，可以按最大长度作教学化排列：

```text
H1：10 23 48 --
H2：10 77 63 90
H3：10 54 -- --
```

这里的 `--` 只是示意占位，并非论文中真实的物理 Block 编码。实际实现还涉及 Head、Layer 与物理 Block 的映射、元数据组织，以及不同展平方式之间的开销权衡。

### 4.5 这三个方法为什么不是简单的“选最省操作的一个”？

Rewrite 可能付出较高的前期成本，却让后续 Attention 更快；Sparse Loading 可能准备成本小，却保留更多不规则访问和执行开销。只有综合**压缩频率、KV 数量、元数据准备时间、后续使用次数和硬件条件**，才能判断具体策略是否划算。

所以，今天最重要的一个新认识是：

> **算法层面的 KV 稀疏率，不等于系统层面的端到端加速比。**

## 五、我对 HARD-KV 三个机制的整体理解

| 机制 | 主要问题 | 今天的理解 |
|---|---|---|
| Cascade Cache | 新旧 KV 如何分层管理？ | 近期完整、历史动态选择、较老数据进一步规整或压缩 |
| Logits Calibration | 不同评分方式怎样共用 Top-p？ | 在尽量保持选择排序的前提下，校准累计概率质量 |
| Index Regularization | 动态选择如何高效执行？ | 在不规则 Mask 与规则物理布局之间平衡准备和计算成本 |

它们之间并不是三段独立的优化：**Top-p 给出动态选择，缓存层次决定这些结果如何保存，而索引规整决定其在 GPU 上如何真正执行。**

## 六、今天的理解变化

### 我原本主要关注什么？

阅读 KV Cache 压缩论文时，我主要关注**应该保留哪些 token，以及保留多少 token**，容易把压缩率直接等同于计算效率的提升。

### 现在的理解

今天进一步认识到：即使已经完成 Head-wise 重要性选择，还会存在概率尺度、KV 生命周期和实际硬件布局三方面的问题。更细粒度的选择可能降低有效 KV 数量，但也可能提高索引处理与调度的复杂度。

### 为什么有这个变化？

一方面，Top-k 相同但 Top-p 不同的例子说明，**排名正确不等于概率预算合理**。另一方面，不同 Head 生成不同长度、不同位置的 KV 索引，说明**算法上的稀疏结构未必直接适合 GPU 高效执行**。

## 七、值得继续研究的问题

以下是阅读后的问题，不代表已经通过实验验证：

1. **温度校准是否能稳定适配不同任务？** 如果当前请求中的注意力分布变化很大，复用同一温度会带来多大误差？
2. **什么时候 Rewrite 值得执行？** 是否能建立一个由整理成本、未来 Decode 次数与预计节省时间共同决定的阈值？
3. **Head-wise 选择越精细越好吗？** 当索引元数据与数据搬运开销增加时，是否存在一个最优粒度？
4. **与 CompressKV 的联系：** 能否在语义检索 Head 的选择依据与 HARD-KV 的动态系统管理之间找到协同方式？这是待验证的研究方向，不是已有实验结论。

## 九、今日总结

HARD-KV 让我认识到，KV Cache 压缩不是单一的“评分—淘汰”问题：**既要让不同 Head 合理选择历史信息，也要让概率校准、缓存生命周期和实际 GPU 执行结构相互配合。**相比单纯提高稀疏率，最终能否降低端到端延迟是更值得关注的系统指标。
