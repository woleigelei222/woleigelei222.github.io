# FreqKV 精读收尾：从压缩后的 Attention 到动态缓存与 RoPE

> **学习记录｜2026-11-09**  
> 本文延续前几天对 FreqKV 中正交 DCT、频率截断、IDCT 及幅值修正的学习。今天重点回答三个问题：压缩后的 K/V 怎样继续计算 Attention？在 Decode 阶段不断产生新 Token 时，缓存如何更新？压缩与 RoPE 为什么不能直接交换执行顺序？

## 一、从数学压缩走到真实推理

前面已经用一个四个 Token 的例子，把一个 Key 通道从四个原始数压缩为两个状态：

\[
K=[1,2,3,4]\quad\longrightarrow\quad
\widetilde K=[1.38478,3.61522].
\]

同样地，如果对应 Value 为 Key 的两倍，可以得到：

\[
V=[2,4,6,8]\quad\longrightarrow\quad
\widetilde V=[2.76956,7.23044].
\]

这里必须先澄清：**压缩后的两个状态不是“从原始四个 Token 中留下两个”**，而是将整个序列沿 Token 维度进行频域变换、截断、短长度逆变换与幅值修正后得到的新表示。接下来模型仍可使用标准 Attention，只是参与计算的历史 K/V 数量发生了变化。

## 二、手算：压缩前后的 Attention 到底差多少？

为了只观察历史缓存的影响，我采用教学简化条件：单通道 \(d=1\)、新 Query 取 \(q=1\)，并暂时不加入当前 Token 自身的 K/V。**以下数字只是用来验证算法链路，并不是论文提供的实验误差。**

### 2.1 未压缩：四个历史状态

标准 Attention 公式为：

\[
O=\operatorname{Softmax}\!\left(\frac{QK^\top}{\sqrt d}\right)V.
\]

因为 \(q=1,d=1\)，Attention Score 为：

\[
S=qK^\top=[1,2,3,4].
\]

将它们输入 Softmax：

\[
P=\frac{[e^1,e^2,e^3,e^4]}{e^1+e^2+e^3+e^4}
\approx[0.03206,0.08714,0.23688,0.64391].
\]

再对 Value 加权求和：

\[
\begin{aligned}
O&=0.03206(2)+0.08714(4)+0.23688(6)+0.64391(8)\\
&\approx\boxed{6.98531}.
\end{aligned}
\]

第四个历史位置对应的 Key 最大，因此在这个例子中获得的注意力权重也最大。注意：这是由特定 \(q,K\) 的数值关系造成的，并不意味着实际模型总是偏爱最近的 Token。

### 2.2 已压缩：两个新状态

压缩后的缓存为：

\[
\widetilde K=[1.38478,3.61522],\qquad
\widetilde V=[2.76956,7.23044].
\]

新的 Score 与权重分别是：

\[
\widetilde S=[1.38478,3.61522],
\]

\[
\widetilde P=\operatorname{Softmax}(\widetilde S)
\approx[0.09705,0.90295].
\]

最终输出：

\[
\begin{aligned}
\widetilde O&=0.09705(2.76956)+0.90295(7.23044)\\
&\approx\boxed{6.79751}.
\end{aligned}
\]

对比结果如下：

| 指标 | 原始历史 KV | 压缩后历史 KV |
| --- | ---: | ---: |
| 状态数量 | 4 | 2 |
| Attention 输出 | 6.98531 | 6.79751 |
| 与原始输出的绝对差值 | — | 约 0.18779 |
| 相对输出误差 | — | 约 2.69% |

这个例子让我理解了两件事。第一，**频域压缩没有改变 Attention 的基本公式，而是改变了公式的输入**；第二，即使 Key 和 Value 的整体趋势得以保留，Softmax 仍会在新的两个状态上重新归一化，输出因此不可能被保证严格相等。

不能把这里的“状态数量减半”直接说成“模型推理加速 50%”，也不能把 2.69% 当作 FreqKV 在真实任务中的误差上界。实际效果还受多头多层结构、注意力内核、缓存布局和数据内容影响。

## 三、压缩不是一次性的：Decode 阶段怎样更新 KV？

接下来我关注的是更加接近部署场景的问题：模型在 Decode 阶段持续生成 Token，刚压缩好的缓存很快又会增长，怎么办？

FreqKV 的思路是**周期性重复频域压缩**。为了保持和前面手算一致，假设可压缩工作区容量为四个状态，每次压缩后留下两个：

1. 首次写满：原始四个状态 \([1,2,3,4]\)，压缩为 \([C_1,C_2]\)。
2. 继续生成：两个新 Token 的 KV 进入空位，工作区成为 \([C_1,C_2,K_5,K_6]\)。
3. 再次写满：把旧的压缩状态与新原始状态共同作为下一轮压缩的输入。
4. 压缩后重新腾出空位，等待后续生成继续写入。

可以概括成：

```text
工作区写满 → 频域压缩历史 KV → 释放缓存位置
       ↑                              ↓
再次写满 ← 新生成的 Token 持续写入空位
```

需要注意第二轮的 \(C_1,C_2\) 已经不是完整的原始 Key/Value。因此，**重复压缩不等价于一直保存全部原始历史，然后最后只做一次压缩**。从这一点可以推导出一个值得验证的风险：越早进入缓存的信息，可能经历更多次有损变换，其局部细节在多轮压缩后更容易受到影响。但风险大小不能仅凭推导定量断言。

### 3.1 为什么保留 Sink Tokens？

一些 Attention Head 对序列开头位置有较稳定的注意力行为。笔记所讨论的 FreqKV 机制将 Sink Token 的原始缓存与可压缩的历史区域区分处理，不把开头的这些状态直接卷入反复的频域压缩，以免改变其位置和表示特性。

这里的 Sink 与“重要 Token Top-k”不是同一个概念：Sink 更强调具有特殊注意力行为的开头位置，而 Top-k 通常依据某种评分从历史位置中做筛选。

### 3.2 Prefill 和 Decode 的触发方式不同

| 阶段 | 输入方式 | 缓存增长方式 | 压缩触发逻辑 |
| --- | --- | --- | --- |
| Prefill | 长 Prompt 按 Chunk 分块处理 | 一批新增多个 KV | 随分块处理和缓存容量管理进行压缩 |
| Decode | 逐步生成新 Token | 通常每一步加入一个 KV | 缓存达到阈值时再重复压缩 |

两者使用的是同类频域压缩机制，区别主要在**输入 Token 进入缓存的节奏和触发时机**。分块 Prefill 并不意味着 Chunk 之间完全无法相互注意；当前块仍要利用此前保留的历史信息。

## 四、RoPE 为什么不能随便放到压缩前？

前面的单通道示例忽略了位置编码，实际 Transformer 的 Key 是多维向量。RoPE 会依据位置对 Query 和 Key 施加旋转。如果多个位置的 Key 在旋转后才被合并，压缩过程混合的不再只是原始特征，还包括不同位置产生的旋转差异。

为了看清这一点，我用两个二维 Key 做一个**人为设定 90° 相邻旋转角度**的教学例子；它不是实际模型的固定旋转角。

\[
k_0=[1,0],\qquad k_1=[1,0].
\]

**方案 A：先 RoPE，后压缩。** 若两个位置的旋转角分别为 \(0^\circ\) 与 \(90^\circ\)：

\[
k'_0=[1,0],\qquad k'_1=[0,1].
\]

对于 \(N=2,L=1\)，沿序列保留直流系数、进行一点 IDCT 并乘幅值修正，结果等价于取均值：

\[
\widetilde k_A=\tfrac12([1,0]+[0,1])=[0.5,0.5].
\]

**方案 B：先压缩，后按新槽位 RoPE。** 先合并未旋转的 Key：

\[
\widetilde k=\tfrac12([1,0]+[1,0])=[1,0].
\]

如果教学例子中把这个压缩状态放在位置 0，那么施加该槽位的 RoPE 后仍得到 \([1,0]\)。两种顺序的结果不同：

\[
[0.5,0.5]\neq[1,0].
\]

这个例子说明**RoPE 与压缩运算一般不可交换**。按照所读 FreqKV 的处理顺序，先以未加 RoPE 的 Key 完成频域压缩，再依据压缩后缓存的槽位安排位置编码；Value 本身不施加 RoPE。这样主要解决的是压缩状态的**位置编码适配**，不代表能恢复每个原始 Token 的精确位置或顺序信息。

## 五、我对 FreqKV 的理解变化

**原本的认识：** KV Cache 压缩主要是删除部分历史 Token，压缩率越高，缓存自然越省；DCT 则是另一种数学表示变换。

**现在的认识：** FreqKV 将历史 K/V 先变为频域表示，再截断和重新构造更短的缓存状态。它不只涉及压缩算子本身，还需要解决后续 Attention 如何计算、缓存何时再次压缩，以及压缩位置如何与 RoPE 配合。算法可用与否，需要从完整推理链路来判断，而不是只看一维序列能否近似重建。

**促使认识变化的过程：** 自己算过原始与压缩后的 Softmax，发现“保留整体趋势”仍会改变每个 Query 的输出；进一步追踪 Decode 的工作区更新和 RoPE 的处理顺序后，才意识到位置语义与长期迭代误差同样重要。
