# 从 SSD 感知调度到稀疏 Attention：五篇论文的阶段性复盘

## 今天的学习主线

今天的学习主要分为两部分：首先继续阅读 **SolidAttention**，理解第三个挑战——数据一致性，以及作者如何通过任务依赖和调度机制实现 GPU 计算与 SSD I/O 的安全重叠；然后回顾近期阅读的 **EdgeAutoOffloadAI、DSA、SATIN 和 PADE**，尝试把各篇论文放在同一条研究脉络中理解。

与单纯记住论文使用了哪些算法相比，我今天更想弄清楚：**一项优化为什么被提出，它减少了什么成本，又可能引入什么新的成本？**

## 一、SolidAttention：为什么计算和 I/O 重叠会引起数据一致性问题？

### 1.1 从 GPU 等待 SSD 开始

长上下文推理中的 KV Cache 可能超过设备的可用内存，因此一部分历史 KV 需要保存在 SSD 上。如果严格按照“读取完成，再开始 Attention”的顺序执行，GPU 就可能长期等待 I/O。

一个自然的思路是让两个过程重叠：

```text
GPU：计算当前层的 Attention
SSD：预取下一阶段可能需要的 KV
```

但在有限缓冲区中，异步读写不能随意进行。假设 **Buffer A** 仍然保存着 GPU 尚未使用完的 KV，系统却错误地认为这块空间已经空闲，允许 SSD 将新的 KV 写入，那么 GPU 就可能读到被覆盖或混杂的数据。

这里需要区分两个“复用”：

- **KV Cache 复用**：再次利用之前计算好的 KV，避免重复计算。
- **Buffer 复用**：旧数据不再使用后，将同一块内存空间分配给新数据。

只有确定旧数据不再被相关计算使用时，Buffer 才能被安全覆盖。由此我认识到，**并行执行并不是越多越好，首先要保证任务之间的依赖正确**。

### 1.2 DAG：梳理哪些任务可以并行

SolidAttention 将 Attention 过程进一步拆为细粒度任务，并通过 **DAG（有向无环图）** 表示先后依赖。

下面是用于理解的五类任务：

| 任务 | 作用 |
| --- | --- |
| Q Projection | 计算当前 Query |
| KV Projection | 计算当前 token 的 Key 和 Value |
| Selection | 根据 Query 选择历史 KV Block |
| Loading | 从 SSD 加载缺失的 KV Block |
| Attention | 使用已就绪的数据计算注意力 |

例如，`Selection` 必须等待 `Q Projection`，因为它需要当前 Query 才能评估 Block 的相关性；但 `KV Projection` 不一定需要等待 `Selection`，二者有机会并行。真正执行 Attention 前，则必须确保它依赖的 KV 已经准备好。

因此，DAG 帮助系统回答的是：**谁必须先完成，谁可以同时做？**

### 1.3 Critical Path 和 LST：哪些任务应该先执行？

仅仅知道任务是否可以并行还不够。当多个任务都已经就绪时，系统仍然要决定调度优先级。

- **Critical Path（关键路径）**：任务图中决定整体最短完成时间的最长依赖路径。延迟关键路径上的任务，更容易拖慢整个流程。
- **LST（Latest Start Time，最晚开始时间）**：为了不影响目标完成时间，一个任务最迟应该在什么时候开始。LST 越紧迫，通常越值得优先考虑。

我现在把三个概念区分为：**DAG 判断能不能执行，关键路径判断是否影响总时延，LST 帮助确定哪项工作更紧急。**

### 1.4 同步点复用：减少重复确认的开销

当 SSD 加载数据而 GPU 准备使用它时，系统必须确认读取完成，这就是同步。若多个 I/O 任务最终都汇合到同一个 Attention 任务之前，可以尽量利用共同的就绪检查点，而不是为每项操作增加重复的同步等待：

```text
Block A 加载 ──┐
Block B 加载 ──┼──→ 确认所需 KV 均已就绪 → Attention
Block C 加载 ──┘
```

这不是取消必要的同步，而是**在保证数据正确的前提下，减少冗余协调开销**。

### 1.5 一个尚待验证的想法

在这部分阅读结束后，我想到一个问题：**SolidAttention 的 KV 交错布局，能否与 HillInfer 的近存储重要性评分结合？**

目前还不能直接给出肯定答案。SolidAttention 的 K/V 交错布局有利于某些 K/V 联合读取；但 HillInfer 的重要性评分主要依赖 Key，若交错布局导致评分阶段读取原本不需要的 V，也可能增加开销。之后需要进一步比较两篇论文的数据布局、评分过程、硬件条件和真实 I/O 量。

## 二、EdgeAutoOffloadAI：从系统状态学习任务卸载策略

这篇论文研究的是**动态移动边缘计算环境中的任务卸载与资源分配**。任务既可以在本地执行，也可能卸载给边缘服务器，但用户数量、网络条件、任务负载与可用算力会持续变化，固定规则难以始终做出合理决策。

作者将 **Transformer 与 PPO** 结合：Transformer 负责刻画用户、任务、服务器之间的复杂关联；PPO 通过与模拟 MEC 环境交互，学习卸载和连续资源分配策略。我现在习惯将它概括为：**Transformer 帮助理解局势，PPO 学习采取什么行动。**

PPO 的典型裁剪目标为：

\[
L^{\mathrm{CLIP}}(\theta)=\mathbb{E}_t\left[\min\left(r_t(\theta)\hat A_t,\operatorname{clip}(r_t(\theta),1-\epsilon,1+\epsilon)\hat A_t\right)\right]
\]

其中，\(r_t(\theta)\) 是新旧策略概率比，\(\hat A_t\) 是优势估计，\(\epsilon\) 是裁剪参数。裁剪的直观作用是**限制一次策略更新过大的变化**，而不是保证每个决策都绝对保守。

为了避免只追求平均时延，论文还考虑了公平性与尾部风险。Jain 公平性指数为：

\[
J(x_1,\dots,x_n)=\frac{(\sum_i x_i)^2}{n\sum_i x_i^2}
\]

在指标定义合理的前提下，指数越接近 1，用户之间的服务水平越均衡。**CVaR** 则关注高时延事件的尾部损失，而不只是平均值，也不能简单等同于“最慢的一次任务”。

这篇论文让我建立了系统级动态优化的基础：任务往哪里执行、资源如何分配，不仅要考虑时延，还要考虑能耗、公平性和极端风险。后续论文虽然逐渐深入 Attention 和 KV Cache，但这种**多目标、动态权衡**的思路仍然很有参考价值。

## 三、DSA：动态决定哪些注意力连接值得保留

从 DSA 开始，我的阅读重心转向边缘设备内部的 Attention 计算。

标准 Self-Attention 中，\(N\) 个 token 对应 \(N\times N\) 个 Query-Key 关系位置，主要计算量通常与 \(O(N^2d)\) 有关。但不是所有 token 对都同样重要，因此 DSA 希望根据当前输入动态调整稀疏模式。

它的一种掩码表示形式为：

\[
M=\mathbf{1}[g_\phi(Q,K)>\epsilon]
\]

其中 \(g_\phi\) 是评分网络，\(\epsilon\) 为阈值，掩码的 1 和 0 分别表示保留或屏蔽连接。论文还利用信息熵等统计特征帮助预测，让不同 Attention Head 根据输入保留不同数量的连接。

由于论文面向 RGB、LiDAR、IMU 等多模态传感器，作者还考虑**跨模态特征对齐**：如果两种传感器的信息本来没有对应好，稀疏选择就可能误删真正重要的联系。

硬件部署时，单纯减少连接数量也不够。保留连接若十分零散，仍然会产生不规则访存、索引和调度开销。因此论文进一步采用：

- **Block-Sparse**：将稀疏执行组织成较规律的计算块。
- **Operator Fusion**：减少兼容算子之间的中间读写与 Kernel 启动。
- **混合精度量化**：根据不同运算对精度的敏感性分配不同位宽。

这篇论文给我的重要提醒是：**理论 FLOPs 减少，不等于真实时延一定下降。** 动态掩码生成本身也有成本；稀疏度过高还可能导致有用信息被删除。这些问题又引出了后续的位级计算与硬件执行优化。

## 四、SATIN：把剪枝和混合精度统一为位宽控制

SATIN 延续了稀疏 Attention 的研究，但关注点更偏向专用指令集与软硬件协同。

普通稀疏方法会判断哪些连接需要保留，但即使两个 token 都被保留，它们的重要性仍可能不同。**为什么一定要对二者使用相同的计算精度？**

SATIN 将稀疏剪枝理解为精度分配的特殊情况：重要 token 可以分配较高位宽，较不重要的 token 使用较低位宽，被剪枝的连接相当于分配 **0 bit** 的后续计算预算。

系统从 **MSB（最高有效位）**开始计算 QK 部分结果，逐渐获得重要性信号，并据此控制后续运算。不过，仅凭部分高位还不能直接断言最终分数大小；仍需结合剩余位的不确定性和误差控制作决策。

此外，Attention 输出为：

\[
O=\sum_{i=1}^{N} a_iV_i
\]

若某个 \(a_i\) 较小，则在权重固定的简化分析中，对应 \(V_i\) 的近似误差对最终输出的影响也会被较小权重缩放。因此作者希望根据重要程度调整 Value 的计算精度，并进一步决定 KV Cache 需要读取多少位平面。

SATIN 的三个重要硬件模块是：

| 模块 | 作用 |
| --- | --- |
| QK Unit | 计算 Query 与 Key 的位级部分和 |
| IMP Unit | 根据部分结果评估重要性 |
| PV Unit | 根据分级精度执行加权 Value 累加 |

论文还通过全局误差预算约束精度分配。它让我理解到：**稀疏不仅是“算还是不算”，也可以是“分配多少计算精度、读取多少数据”的统一资源决策。**

## 五、PADE：能否不再为剪枝单独增加预测器？

PADE 又提出了更具体的问题：如果稀疏 Attention 需要一个独立 Predictor 先判断哪些 QK 对重要，那么 Predictor 自身也需要计算与访存，它带来的额外成本是否抵消了一部分稀疏收益？

因此 PADE 采用 **Stage Fusion（阶段融合）**：不再把预测与执行完全分开，而是从 Key 的高位开始正式计算 QK 分数，直接用中间部分结果判断能否提前终止。

### 5.1 BUI-GF：为什么不能看到部分分数低就直接剪枝？

假设某个分数最后可能达到 8，但高位部分和目前只有 6。如果保留阈值为 7，直接依据 \(6<7\) 剪枝就可能误删重要连接。

PADE 通过 **BUI-GF** 建立位级不确定区间，用上界和下界描述尚未计算的低位可能造成的影响。可以用简化形式理解：

\[
S\in[L,U]
\]

只有当可靠上界已无法满足某个保留条件时，才可以依据相应剪枝规则提前终止。这里的“安全”依赖具体边界与决策条件，不代表在任意激进稀疏配置下，任务准确率都不受影响。

### 5.2 BS-OOE：位级任务为什么需要乱序执行？

不同 Key 可能在不同 bit 被剪枝，导致处理单元的工作量不一致。有的 PE 很快结束，有的仍在计算或等待下一位数据。如果必须所有 PE 一起等待，就会浪费硬件资源。

PADE 通过 **BS-OOE** 重新安排就绪任务，使部分 Key 等待 DRAM 数据时，PE 可以去处理其他工作。其中：

- **Scoreboard** 记录未完成 Key 的部分和、位级进度与状态。
- **Scheduler** 决定下一项就绪工作由谁执行。

这样可以避免因某个 Key 被剪枝或等待数据，就让计算单元长时间空闲。

### 5.3 ISTA 与 RARS：怎样兼顾 Tile、Softmax 和数据复用？

为适应片上存储容量，Attention 通常需要分块执行，但 Softmax 的归一化与整行分数相关，无法完全脱离其他 Tile 进行判断。

由于同一行 Softmax 保持精确分数的大小排序：

\[
s_i>s_j\Rightarrow\operatorname{softmax}(s)_i>\operatorname{softmax}(s)_j
\]

PADE 可以利用这一性质，协调稀疏剪枝与分块执行。论文还使用 **RARS** 改善 Value 访问顺序，尽量减少重复加载。

这让我进一步认识到：**稀疏 Attention 的收益不仅取决于剪了多少 QK 对，还取决于 PE 利用率、数据布局、分块执行与 I/O 复用。**

## 六、今天最重要的理解变化

### 我原本以为

开始阅读这些论文时，我容易将优化理解成单一方向：稀疏就是减少计算，量化就是减少 bit，预取就是提前读数据，并行就是让 GPU 和 SSD 一起运行。每项机制似乎都能直接带来性能收益。

### 现在我的理解是

**每一种优化都会改变系统中其他环节的成本结构。**

- DSA 减少部分 Attention 计算，但掩码生成和不规则访存也需要成本。
- SATIN 按重要性分配位宽，但必须控制近似误差并设计相应硬件。
- PADE 将预测与执行融合，却还需要解决 PE 负载不均与分块数据复用。
- SolidAttention 提前加载 KV，但必须管理缓冲区生命周期、依赖和同步，才能安全地重叠计算与 I/O。

所以我现在更关注**一项优化最终是否降低了端到端时延，而不是只看某个局部指标是否改善**。

### 为什么我的理解发生变化

过去我更多把每篇论文当作一套独立方案。现在回过头看，很多方法实际上是在处理前一类优化引入的新问题：减少计算后出现预测成本，提前传输后出现同步与数据一致性问题，稀疏化后又出现硬件执行不规则的问题。

从系统级任务卸载，到 Attention 算法，再到硬件和 SSD 调度，这种“瓶颈不断转移”的现象逐渐成为我阅读论文时最关注的线索。

## 八、今天还没有解决的问题

1. **SolidAttention 与 HillInfer 的方案是否兼容？** KV 交错布局可能减少联合读取请求，但也可能让只需要 Key 的重要性评分产生多余访问，需要对比实际数据流。
2. **DAG/LST 与 PADE 的 Scoreboard/乱序执行有什么本质区别？** 两者都减少等待，但任务粒度和依赖对象不同，值得画图比较。
3. **怎样衡量稀疏 Attention 的真实收益？** 除稀疏率之外，应同时记录预测、数据重排、访存、同步和硬件利用率的成本。
4. **目前主要停留在论文机制理解。** 尚未开展相应的代码复现与实测，不能把作者的实验收益当作我自己的实验结果。

## 九、下一步最小行动

下一次沿着 KV Cache 研究路线继续回顾 **MTDS、DUAL-BLADE 和 HillInfer**，重点画出一条数据流：KV 存放在哪里、如何判断重要性、通过什么 I/O 路径搬运、最终何时交给 GPU 计算。

等这些部分串起来，再回到今天提出的“SolidAttention × HillInfer”想法，判断它是否值得进一步做实验验证。

## 今日总结

今天最大的收获，不只是弄清了 SolidAttention 的第三个挑战，更是开始理解各篇论文的研究问题怎样逐步深入。

> **好的优化不只是把某一项计算做得更少，而是要保证额外的判断、数据搬运、调度与同步成本不会抵消收益。**

之后阅读新的边缘 LLM 论文时，我希望继续追问：作者减少了哪一部分成本？额外引入了什么成本？瓶颈是否转移？最终端到端表现是否真的改善？
