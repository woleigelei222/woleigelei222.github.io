# 边缘 LLM 学习：在线联合优化的收尾与 EdgeShard 协同推理框架初探

> **学习记录｜2026-11-13**  
> 前篇：*Co-Optimizing Request Scheduling and KV Caching for Edge LLM Serving*（IEEE Internet of Things Journal，2026）  
> 新篇：*EdgeShard: Efficient LLM Inference via Collaborative Edge Computing*（IEEE Internet of Things Journal，2025）  
> 本文记录两项连续的学习内容：先总结请求调度与缓存协同中的在线决策，再进入 EdgeShard 的研究动机与系统架构。文中的小规模数值为教学示例，不是论文实验数据。

## 一、从昨天的问题出发：为什么调度不能只看眼前？

上一份笔记讨论了动态 KV Block 管理与时空耦合。今天继续追问：**未来请求不可预知，当前请求应该交给哪台边缘服务器？**

假设请求 $R_1$ 需要公共前缀 $P$，系统有 A、B、C 三台服务器：

| 节点 | 是否缓存 $P$ | 排队等待 | 前缀计算或复用开销 | 当前简化合计 |
| --- | --- | ---: | ---: | ---: |
| A | 是 | 100 ms | 10 ms | 110 ms |
| B | 否 | 20 ms | 150 ms | 170 ms |
| C | 是 | 60 ms | 15 ms | **75 ms** |

在只考虑排队和前缀处理的简化模型中：

$$
T_A=100+10=110\ \mathrm{ms},\quad
T_B=20+150=170\ \mathrm{ms},\quad
T_C=60+15=75\ \mathrm{ms}
$$

当前请求选择 C 的代价最低。但如果调度器只盯着这个数字，就可能忽略选择本身对后续缓存状态的影响。

### 1.1 排队短，不代表 KV 缓存空间充足

这里需要澄清一个容易混淆的问题：**节点 C 当前没有明显排队压力，不等于它有空余缓存空间。**排队时间反映当前计算服务的等待情况；KV Cache 占用可能来自此前处理完成、为后续复用而保留的历史前缀。

假设 C 的可复用缓存已经占满三个 Block 位置：

$$
C_{\mathrm{cache}}=[P,X,Y]
$$

$P$ 是当前请求可复用的公共前缀，$X$、$Y$ 是历史请求留下的、允许淘汰的非活跃缓存。现在 $R_1$ 还需要处理新的输入 $Z$，若系统希望把 $Z$ 对应的 KV 也长期保存在同一固定容量中，就可能需要淘汰一个旧 Block，例如：

$$
[P,X,Y]\longrightarrow[P,Y,Z]
$$

若下一个请求恰好需要 $X$，它就无法在 C 上直接命中 $X$。但这只是**假设发生缓存替换**的教学情境，不代表每次生成新 KV 都必然驱逐旧 Block；实际系统也可能选择不保留新缓存、转移存储或采用其他内存管理方式。当前请求仍在使用的活跃 KV 也不能随意淘汰。

### 1.2 当前代价与长期代价的区别

可以用一条因果关系概括：

```text
当前请求到达
    ↓
选择处理节点 + 决定是否保留新 KV
    ↓
节点队列、缓存占用与热点分布改变
    ↓
下一批请求的命中率与等待时间发生变化
    ↓
下一次调度再次基于新状态做决策
```

**空间耦合**来自不同设备的计算能力、带宽与缓存内容不同；**时间耦合**来自当前调度会改变下一时刻的可用资源。这个认识也提醒我：不能把一次请求的最小等待时间直接当作整个服务周期的最优策略。

## 二、在线联合优化：不知道未来，也要做出可执行决策

### 2.1 Online 并不是“服务器联网”

在线优化（Online Optimization）指：新请求到达时，调度器只能利用当前已经观察到的请求、队列、缓存和设备资源信息作出决定；等后续请求出现，再根据更新的状态继续决策。它不能默认已经知道未来全部请求的到达时刻和内容。

这使问题比静态分配复杂：调度需要及时执行，缓存决策又可能产生长期后果。**在线联合优化的重点不是只挑一个最快节点，而是同时考虑请求分配与缓存状态更新。**

### 2.2 随机舍入为什么会出现在这个问题中？

先用一个最小化的数学例子理解随机舍入（Randomized Rounding）。假设一个请求只能选择 A、B、C 中的一台设备，定义二元变量：

$$
x_A,x_B,x_C\in\{0,1\},\qquad x_A+x_B+x_C=1
$$

为了便于处理离散优化，有时先求一个连续松弛解：

$$
0\le x_A,x_B,x_C\le1,\qquad
(x_A,x_B,x_C)=(0.2,0.3,0.5)
$$

这个连续解不能直接执行，因为一个不可拆分的请求不可能以 20%、30%、50% 的比例分别交给三台设备。一个最直观的教学舍入方法是把这些数当作概率：

| 随机数 $u$ 的范围 | 分配节点 |
| --- | --- |
| $0\le u<0.2$ | A |
| $0.2\le u<0.5$ | B |
| $0.5\le u<1$ | C |

例如取 $u=0.63$，由于 $0.5\le0.63<1$，本次将请求分配给 C：

$$
(x_A,x_B,x_C)=(0,0,1)
$$

**这只是用于理解随机舍入的基础例子，并不是原论文算法的完整实现。** 它没有展示作者如何构造松弛、设置依赖关系或证明性能界。

### 2.3 为什么不能不加约束地独立随机选择？

因为边缘系统存在真实容量限制。假设 C 目前只剩一个请求的执行名额，两个请求分别独立随机分配，就可能同时被选到 C，导致容量约束被破坏。缓存空间、路由可达性和 Block 占用也会影响方案是否合法。

因此，**有概率分布不等于有可执行的调度策略**。需要将资源约束纳入优化或舍入程序。针对前篇论文，今天主要理解了在线决策与随机舍入的动机；作者具体的随机化步骤、可行性处理以及理论保证，还需以原文算法和定理为准，不能从这个三节点概率例子直接推断。

## 三、转向 EdgeShard：从缓存调度走向多设备协同推理

完成对在线联合调度的初步梳理后，今天开始阅读新论文：

**EdgeShard: Efficient LLM Inference via Collaborative Edge Computing**  
作者：Mingjin Zhang、Xiaoming Shen、Jiannong Cao、Zeyang Cui、Shan Jiang  
来源：*IEEE Internet of Things Journal*，2025，12(10): 13119–13131  
DOI：https://doi.org/10.1109/JIOT.2024.3524255

### 3.1 研究动机：单台边缘设备容不下完整 LLM

将 LLM 完全部署在远端云端，可能产生较高的网络往返时延、数据传输成本和隐私顾虑；直接放在边缘端，又常常受到显存、算力的限制。EdgeShard 将问题重新表述为：**能否把模型按层划成多个 Shard，再从异构边缘设备与云节点中选择合适的参与者，共同完成推理？**

例如，一个 12 层的教学模型可以按顺序切为三个连续分片，由三个设备分别执行。分片并非一定平均：计算速度、内存容量和设备间带宽都会影响划分位置。

### 3.2 三阶段框架：先测量，再决策，最后执行

原论文 Figure 3 展示了 EdgeShard 的整体框架：

| 阶段 | 输入或依据 | 需要完成的事情 |
| --- | --- | --- |
| 离线 Profiling | 模型层、设备与链路 | 测量各层在不同设备上的计算成本、输出大小、内存需求以及设备和网络参数 |
| 联合设备选择与模型划分 | 第一阶段的性能画像 | 确定哪些设备参与、每台设备承担哪些连续模型层 |
| 在线协同推理 | 确定的分片部署方案 | 按顺序方式或流水线方式执行推理 |

**Profiling 记录什么？**

- 计算时间 $t^{\mathrm{comp}}_{i,j}$：模型第 $i$ 层在设备 $j$ 上的执行时间；论文区分测量 Prefill 与生成阶段，并采用平均测量值用于优化。
- 层内存需求 $Req_i$：判断设备是否能容纳分配给它的模型层；设备无法整体加载时，可以用动态加载分片进行测试。
- 层输出大小 $O_i$：决定跨设备传输中间激活的数据量。
- 设备预算 $Mem_j$ 与带宽 $B_{k,j}$：分别约束存储可行性与设备间通信开销。

为什么需要提前测量？因为哪怕两台设备都能运行某个分片，**算得快的设备也可能因为传输慢而使总时延变大**。

### 3.3 第一个模型层为什么留在源设备？

EdgeShard 在时延优化问题中设置首层驻留源节点的约束：

$$
X_{0,0}=1
$$

含义是第一层的计算必须在用户输入所在的源设备完成，以避免把原始输入直接转发给其他计算节点。**这是一项降低原始数据传输风险的设计，并不意味着后续跨设备传输的中间激活绝对不会泄露信息。**

### 3.4 两种协同执行方式

- **顺序推理（Sequential Inference）：** 一份输入沿模型层的分片顺序依次通过各设备，重点是减小单次推理时延。
- **流水线并行（Pipeline-Parallel Inference）：** 将一批请求或输入划成多个 Micro-batch，不同设备可在同一时刻处理不同 Micro-batch，重点是提升资源利用率和整体吞吐量。

流水线的一个重要前提是：同一个 Micro-batch 的相邻层、前后生成 Token 仍要满足依赖关系，不能因为设备并行就跳过计算顺序。有关模型层分配的动态规划和自回归流水线调度，留到后续精读。

## 四、今天最重要的理解变化

今天的两个学习主题看似不同，但都让我把注意力从局部最快转向**系统整体可行、可持续的运行状态**。

首先，在请求调度问题上，排队时间和显存占用不能混为一谈。节点即使不忙，也可能因为保留了历史 KV Block 而没有空闲缓存位置；当前请求的选择会影响后续命中情况。

其次，在线优化中的概率解只是一个中间表示。连续解必须在资源约束下转换成真正可执行的离散决策，不能认为随机选择天然满足显存或节点负载约束。

最后，在 EdgeShard 的阅读中，我开始把“单机无法容纳 LLM”理解为一个**异构计算资源、模型分片与网络通信联合配置**的问题。下一步需要进一步理解作者的具体目标函数与两套动态规划。
