# ThinKV 精读（二）：从渐进式 KV 淘汰到缓存槽位复用

> **学习日期：** 2026 年 10 月 22 日  
> **阅读论文：** *ThinKV: Thought-Adaptive KV Cache Compression for Efficient Reasoning Models*（ICLR 2026）  
> **本次范围：** TBE（Think Before You Evict）、Continuous Thinking（CT），以及由此产生的研究思考。  
> **记录边界：** 本文是当天论文学习的整理，并非本人完成了代码复现或性能实验；文中的机制来自论文，数值演示主要用于帮助理解。

## 一、今天要解决的两个问题

昨天主要学习了 ThinKV 怎样根据 Thought 类型为 KV 分配不同量化精度。今天继续向下思考：

1. 即使单个 KV 已经变小，随着 Decode 生成越来越多的 token，**历史 KV 的数量**还是会持续增长，能否进一步减少？
2. 删除历史 token 往往会在 GPU 缓存里留下分散的空位，**如何回收这些位置，而不是反复搬运仍然有效的 KV**？

对应地，论文给出了两个相互衔接的机制：

- **TBE** 负责决定历史 Thought 应该留下多少 KV、留下哪些 KV；
- **CT** 负责在物理缓存层面管理和复用被淘汰的槽位。

这也让我逐渐意识到：KV Cache 优化不是只有“算出应删除哪些数据”这一步。算法选择与实际硬件执行之间，还隔着内存布局和索引管理。

## 二、TBE：为什么以 Thought 为单位淘汰，而不是逐 token 淘汰？

### 2.1 Transition 可以成为渐进压缩的触发信号

论文分析了长链式推理中不同 Thought 片段之间的依赖关系。一个值得关注的观察是：**当模型发生 Transition，即推理方向产生变化时，之前部分 Thought 对后续生成的影响往往逐渐减弱。**

这不代表过去的推理完全没用了。例如，某次失败的尝试仍可能为后续纠错提供线索。因此，作者没有采取“发生 Transition 就立即清空之前所有 KV”的做法，而是对旧 Thought 执行**渐进式淘汰（progressive eviction）**。

我的理解是：随着推理轨迹继续变化，较早的思考片段可以分配越来越少的缓存预算，但仍应保留有限的历史信息。

### 2.2 逐级保留：128 → 64 → 32 → 16 → 8 → 4

在论文的主要配置下，一个刷新区间对应 128 个 token，保留档位为：

\[
R=\{64,32,16,8,4\}.
\]

| 状态 | Thought 中保留的 token 数 | 我的理解 |
|---|---:|---|
| 原始状态 | 128 | 尚未执行这一轮渐进压缩 |
| 第一次被选中淘汰 | 64 | 先减半，保留较多历史线索 |
| 第二次被选中淘汰 | 32 | 进一步降低旧片段预算 |
| 第三次被选中淘汰 | 16 | 保留更精简的代表 |
| 第四次被选中淘汰 | 8 | 再次缩减 |
| 第五次及达到下限后 | 4 | 达到论文采用的最低保留数量 |

这里的 **64、32、16、8、4 表示保留数量，不是相应 token 的量化 bit 数**；也不是说每次 Decode 都要执行一次压缩。只有当相关淘汰条件满足，某个旧片段才会降至下一个保留档位。

### 2.3 两类触发条件

**第一类：推理轨迹发生改变。** 当一个 Transition 片段完成，系统可以将先前的历史 Thought 逐步降低到下一档保留数量。

**第二类：缓存容量超过预算。** 如果模型长时间停留在 Reasoning 阶段，没有明显 Transition，KV Cache 仍会增长。因此论文设置缓存预算 \(k\)。当某一层保留的 KV 数量超过预算时，系统会考虑较老且重要性较低的 Thought，继续执行压缩。

第二条让我明白，Transition 并不是系统唯一的淘汰入口：**TBE 同时结合了推理过程变化与实际内存容量约束。**

## 三、K-means：压缩到 64 个时，究竟保留哪 64 个？

知道“保留 64 个”还不够，真正困难的是如何确定具体位置。

直觉上可能想到：选 Attention 权重最高的 64 个 token。但论文没有把这一方式当作 TBE 的主要选择方法，而是根据一个 Thought 内 **Post-RoPE Key 向量的相似性**执行 K-means 聚类，寻找代表性 KV。

### 3.1 K-means 的直观理解

如果一个 Thought 中若干 Key 的向量非常接近，作者希望利用聚类，将相似的 Key 归到同一簇，并用更少的代表覆盖原来较多的 Key。

经典 K-means 的目标函数为：

\[
\min_{\mu_1,\ldots,\mu_K}
\sum_{i=1}^{N}\min_{1\le j\le K}
\left\|x_i-\mu_j\right\|_2^2.
\]

其中：

- \(N\)：压缩前的 Key 数量；
- \(K\)：目标聚类数量；
- \(x_i\)：第 \(i\) 个 Key 向量；
- \(\mu_j\)：第 \(j\) 个簇的中心。

公式想表达的是：让各 Key 到所属簇中心的距离平方之和尽量小。

**一个今天理解机制用的例子：** 如果一个 Thought 有 128 个 token，第一次淘汰后目标是保留 64 个，那么就可以将 K-means 的目标簇数设置为 64，选择相应代表；下一次目标降为 32，再按新的预算处理。

### 3.2 为什么 Key 聚类不等于随意制造一组新 KV？

今天我还注意到一个值得继续核查的细节：**数学上算出的簇中心，不一定恰好等于缓存里原本某个 token 的 Key。** 同时，Attention 中一个 Key 还必须有对应的 Value。

因此，不能简单地把“一个簇的 Key 均值”与“任意一个 Value”拼在一起，就认为它自然构成了合法的 KV 对。论文对代表 Key 与相应 Value 的保留方式，需要结合其算法和实现描述理解。

这也是我下一次回看论文附录和代码时，值得重点核实的细节之一。

## 四、CT：为什么 TBE 决定删除，并不等于 GPU 能立即高效复用空间？

如果 TBE 淘汰的位置分散在不同的物理 Block 内，传统方法可能需要把剩下的有效 KV 重新 Gather、整理到连续区域。

虽然整理后的缓存看起来更紧凑，但这一过程往往还需要额外读取和写入有效 KV，从而占用 GPU 的 HBM 带宽。

ThinKV 因此提出 **Continuous Thinking（CT）**：尽量避免为了消除零散空位而搬运大量仍然有效的数据，转而使用标记与原位复用。

### 4.1 Eviction Mask：先标记，再等待槽位被复用

CT 为物理缓存块管理 Eviction Mask，记录哪些 token 位置已经被淘汰。

例如，某个 Block 最初保存：

```text
槽位：        0 1 2 3
原来的 token：A B C D
Eviction Mask：0 1 0 1
```

可将其理解为：B、D 已被逻辑上淘汰，相应槽位可以在之后由新的 KV 覆盖，而 A、C 没必要因此被搬到另一个位置。

注意：**逻辑标记淘汰不等于立即物理删除或搬迁。** 真正的空间复用可以等到新的 KV 写入时完成。

### 4.2 扩展 Block Table：记录的不只是物理地址

由于新旧片段可能共享一个物理块，CT 还需要知道每个槽位属于哪段 Thought。除了物理块编号和占用信息，扩展后的 Block Table 还记录：

| 元数据 | 用途 |
|---|---|
| Thought Type | 标识当前 Block 的思考类型 |
| Start Indices | 记录 Thought 片段的逻辑起始位置 |
| Segment Mask | 区分同一物理 Block 内不同 Thought 片段所占的位置 |
| Eviction Mask | 标出已淘汰、可供之后回收的位置 |

其中我最关心的是 **Start Indices 与 Segment Mask**：因为一旦复用了旧位置，物理存储顺序就可能不再和 token 的原始生成顺序一一对应，必须保留足够的元数据来恢复逻辑归属。

### 4.3 Segment Mask 的一个具体例子

假设同一个 Reasoning 类型的 Block 最后呈现为：

```text
物理槽位：      0 1 2 3
当前保存：      A M C N
旧 Reasoning：  1 0 1 0
新 Reasoning：  0 1 0 1
```

A、C 属于较早的 Reasoning 片段，M、N 属于新产生的 Reasoning 片段。它们逻辑上来自不同时间，但在物理上共享这个 Block。

**Segment Mask 的作用不是判断哪个 token 重要，而是区分不同片段对物理槽位的占用关系。**

这也解释了为什么 CT 必须配合扩展索引结构：原位复用节约了搬运成本，却增加了对元数据正确性的要求。

## 五、为什么 KV 的物理排列可以与生成顺序不同？

今天另一个让我印象深刻的知识点是：只要 Key、Value 被同步地重新排列，并维持正确的位置语义，标准 Attention 的结果不会因为 KV 行的存储顺序变化而改变。

标准 Attention 为：

\[
O=\operatorname{Softmax}\left(\frac{QK^\top}{\sqrt d}\right)V.
\]

如果用同一个置换矩阵 \(P\) 同时变换 Key 和 Value：

\[
K'=PK,\qquad V'=PV,
\]

则有：

\[
\operatorname{Softmax}\left(\frac{Q(K')^\top}{\sqrt d}\right)V'
=
\operatorname{Softmax}\left(\frac{QK^\top}{\sqrt d}\right)V.
\]

这并不是说**模型可以忽略 token 生成顺序**，也不是说位置编码可以随意更改。它意味着：在保持原有位置语义、并保证 K 与 V 同步配对的前提下，**逻辑顺序和物理排列可以解耦**。

由此，CT 就能在旧的物理槽位里写入新的 token，而不必单纯为了维持物理时间顺序将其他有效 KV 全部搬迁。

## 六、今天最重要的理解变化

### 我原本的直觉

我之前更容易从算法角度思考 KV 压缩：只要选出不重要的 token，再将它们删除，似乎就能直接减少显存和计算开销。

### 现在我的理解

今天通过 TBE 和 CT，我对完整执行流程有了更清楚的认识：

1. **TBE 确定压缩策略**：某个 Thought 应该保留多少、哪些位置需要淘汰；
2. **Eviction Mask 记录逻辑淘汰**：暂时不必整理所有仍有效的 KV；
3. **Block Table 与 Segment Mask 保留逻辑信息**：确保新旧 Thought 的归属不会混淆；
4. **CT 复用已有槽位**：新的 KV 可以写入相同类型缓存块中可回收的位置。

也就是说，**算法决定删什么，系统实现决定删除操作能否真正转化为性能收益。**

### 为什么我的理解发生变化

我注意到，动态稀疏化可能制造不连续的缓存空洞。若每次为了重新排列而搬运大量有效 KV，节省下来的 Attention 计算可能被额外访存开销抵消。

因此，以前我主要关注“压缩率有多高”，现在也开始关注**压缩频率、数据重排开销、物理布局和实际 GPU 访存**。

## 七、这篇论文引发的两个研究设想

今天的学习不只是理解了 ThinKV，也让我联想到之前阅读的其他 KV Cache 论文。

**想法一：Thought 类型能否与 token 生命周期联合建模？**

既然 ThinKV 根据 Reasoning、Execution、Transition 决定压缩方式，而其他工作会根据 token 的近期性或历史重要性管理缓存，那么是否能够同时考虑“这是什么类型的思考”与“这段历史信息已经多久没有被有效使用”？

目前这只是阅读后产生的研究问题，尚未完成方法设计或实验验证。

**想法二：不同 Thought 是否适合获得不同的 Layer 级缓存预算？**

此前学过的逐层预算分配让我想到：是否可以同时利用层敏感性与 Thought 类型，为不同 Transformer 层中的不同推理片段设置更合适的保留比例？

但这样也会增加元数据和缓存管理复杂度。是否值得，需要在准确率、显存与实际 GPU 延迟之间进行权衡，不能只看理论压缩率。

## 八、还需要进一步弄清楚的问题

1. K-means 得到聚类中心后，实际实现怎样保证被选中的 Key 与 Value 正确对应？

3. 如果把 Thought 类型与逐层预算结合，新增决策和元数据开销是否会抵消压缩收益？
