# 今天读了什么？

今天首先对上一篇阅读的 **Dynamic Sparse Attention（DSA）** 做了一个收尾，然后开始阅读一篇新的论文：

**《SATIN: a sparse attention application-specific instruction-set processor with custom mixed-precision extensions for energy-efficient edge inference of transformer large language models》**

相比上一篇主要关注“如何让 Attention 变稀疏并真正部署到边缘设备”，SATIN 又往前走了一步：

> **它尝试把稀疏、混合精度和 KV Cache 的内存访问统一到同一种位平面精度控制机制里。**

这让我开始从“单一算法优化”继续走向“算法、编译器和硬件共同设计”。

# 先对上一篇 DSA 做一个小结

上一篇论文提出的 DSA 确实通过动态稀疏、混合精度和异构调度降低了边缘端 Attention 的计算、内存和时延开销。

但它也有比较明显的局限。

## 1. 短序列时，动态稀疏可能不划算

如果序列本身很短，Dense Attention 原本的计算量并不算高。

这时 DSA 还要额外执行：

```text
熵计算
+
稀疏率预测
+
Top-k
+
Mask 生成
```

这些额外步骤本身也需要时间。

所以可能出现：

```text
Dense Attention 本来就不贵
↓
DSA 额外引入预测和剪枝开销
↓
节省的计算 < 新增的开销
↓
整体收益下降
```

这让我意识到：

> **轻量化方法并不是在所有输入规模下都一定有效。**

## 2. 极端稀疏并不代表更好

我之前容易把“稀疏率越高”理解成“计算越少，效果越好”。

但实际上并不是这样。

例如：

```text
稀疏 50%
→ 删除大量冗余关系
→ 重要关系仍然能保留

稀疏 65%
→ 仍可以兼顾精度与效率

稀疏 90%
→ 重要关系也可能被删除
→ 小目标、弱关系丢失
→ 精度明显下降
```

因此真正的问题不是：

> 如何让模型尽可能稀疏？

而是：

> **如何找到“足够稀疏但又不损失关键语义”的工作点？**

## 3. 算法收益还取决于硬件条件

DSA 中有 Top-k、排序、动态控制等操作。

NPU 很擅长：

```text
矩阵乘法
张量计算
规则批量运算
```

但未必擅长：

```text
排序
Top-k
动态分支
不规则控制流
```

这时一部分任务可能需要交给 CPU。

一旦出现：

```text
NPU
↓
CPU
↓
NPU
```

频繁的数据搬运和调度就可能吃掉部分加速收益。

这让我进一步确认：

> **算法上的轻量化，必须放到具体硬件上看才有意义。**

# SATIN 要解决什么问题？

SATIN 关注的是 Transformer 大语言模型在边缘端推理时的两个主要瓶颈。

## 1. Attention 的计算开销

随着序列变长，自注意力需要处理越来越多 token 之间的关系。

因此计算开销会迅速增加。

## 2. KV Cache 带来的内存访问开销

在自回归解码中，模型会不断读取之前保存的 Key 和 Value。

也就是说，随着上下文变长：

```text
序列长度增加
↓
KV Cache 增大
↓
反复读取的数据越来越多
↓
内存带宽压力增加
```

SATIN 的思路不是分别解决“稀疏”和“混合精度”，而是尝试把它们统一起来。

# SATIN 最关键的思想：0 bit 也是一种精度

传统上通常把两个问题分开：

```text
稀疏
→ 这个 token 要不要算？

混合精度
→ 这个 token 用多少 bit 算？
```

SATIN 认为，这两个问题其实可以统一成一个问题：

> **这个 token 到底值得分配多少 bit？**

例如：

```text
0 bit
→ 完全不计算
→ 相当于剪枝

2 bit
→ 很低精度

4 bit
→ 中等精度

8 bit
→ 高精度
```

因此：

```text
0 bit → 稀疏
1~7 bit → 不同级别的低精度
8 bit → 高精度
```

稀疏和混合精度不再是两个相互独立的机制，而是统一到：

> **bit-plane precision（位平面精度）**

这个抽象里。

# 为什么从 MSB 开始计算？

对于一个 8 bit 数：

```text
b7 b6 b5 b4 b3 b2 b1 b0
```

越靠左的高位，对最终数值影响越大。

因此 SATIN 不会一开始就把 8 个 bit 全部算完，而是：

```text
先计算最高有效位
↓
得到一个部分结果
↓
判断当前信息是否已经足够
↓
如果已经能判断 token 是否重要
→ 提前停止

如果仍然不确定
→ 继续计算更低位
```

也就是说：

> **容易判断的 token 少算几位，难判断的 token 再继续深入计算。**

# partial sum 和 importance

SATIN 的一个关键点是：

> 它不额外训练一个完全独立的重要性预测器，而是复用 Q/K 计算过程中已经产生的部分和。

整体过程可以简单理解成：

```text
本来就在算 QK
↓
从高位开始得到 partial sum
↓
根据 partial sum 判断 importance
↓
继续决定后面的计算
```

所以这个重要性信号不是额外单独产生的，而是从本来就要做的计算里顺便得到。

这也是 SATIN 统一控制逻辑的基础。

# SATIN 的六步执行流程

我目前把整个系统理解成下面六步。

## 第一步：设置全局精度预算 ε

用户先给出一个全局精度预算：

```text
ε
```

它表示：

> 系统允许为了节省计算和能耗，最多接受多大的误差。

然后编译器结合离线标定的误差传播模型，为：

```text
每一层
+
每一个 Attention Head
```

分配对应的：

```text
位宽
+
稀疏配置
```

## 第二步：通过配置指令写入硬件

编译器得到参数后，通过一条配置指令写入控制寄存器。

这意味着：

> 硬件不需要重新设计，只要通过配置参数就可以调整运行策略。

## 第三步：Q/K 从 MSB 开始计算部分和

Q/K 不一次性用完整精度计算。

而是：

```text
MSB
↓
更多高位
↓
必要时继续到低位
```

逐步得到越来越准确的部分和。

## 第四步：重要性单元做统一判断

根据 Q/K 的部分和，系统估计 Attention 权重。

然后同一个 importance signal 会同时输出三个结果：

```text
1. token 要不要保留？
2. V 侧应该用多少 bit？
3. KV Cache 应该读多深？
```

这三个决定不再由三个独立模块分别完成。

## 第五步：只读取真正需要的 KV 位平面

如果某个 token 只需要低精度：

```text
只读取少量高位 bit plane
```

如果它很重要：

```text
读取更多 bit plane
```

如果完全不重要：

```text
0 bit
→ 不读取
```

因此不仅计算量减少，内存访问量也会下降。

## 第六步：检查误差是否超出 ε

整个 kernel 完成后，系统会计算累计误差界，并与：

```text
ε
```

进行比较。

如果误差仍然在预算范围内，就可以给出该次推理的精度保证。

这也是 SATIN 和普通“经验式剪枝 + 量化”的重要区别之一：

> 它不是只靠实验去看精度掉了多少，而是试图给单次推理提供可验证的误差范围。

# SATIN 最重要的三个机制

我目前认为 SATIN 最关键的部分，就是同一个重要性信号同时驱动三个机制。

## 1. Q/K 侧 token 稀疏

如果某个 token 的估计权重很小：

```text
importance 很低
↓
位宽设置为 0 bit
↓
不再计算
```

所以：

```text
0 bit
=
pruning
=
sparsity
```

## 2. V 侧分级精度

对于被保留下来的 token，也不是全部用同样精度。

而是：

```text
重要 token
→ 分配更多 bit
→ 计算更精确

不太重要的 token
→ 分配更少 bit
→ 降低计算成本
```

也就是说：

> **精度随着重要程度变化。**

## 3. KV Cache 自适应读取深度

普通情况下，模型可能把完整的 K/V 数据都从内存中读取出来。

SATIN 则根据 importance 决定：

```text
重要
→ 读更多 bit plane

一般重要
→ 只读高位

不重要
→ 0 bit，不读
```

这样就实现：

```text
importance
↓
控制计算量
+
控制精度
+
控制内存流量
```

# 今天最重要的理解

## 我原本以为

我之前更容易把：

```text
稀疏
混合精度
KV Cache 优化
```

理解成三个不同的问题。

例如：

```text
稀疏
→ 解决算得太多

混合精度
→ 解决每次计算太贵

KV Cache 优化
→ 解决内存搬运太多
```

## 现在我的理解是

SATIN 让我看到，这三个问题其实可以被一个统一的问题连接起来：

> **一个 token 到底有多重要？**

如果 importance 很低：

```text
0 bit
→ 不算、不读
```

如果 importance 一般：

```text
低 bit
→ 少算、少读
```

如果 importance 很高：

```text
高 bit
→ 多算、多读
```

所以整个系统实际上是在做：

```text
importance
↓
bit-width allocation
↓
决定：
要不要算
算多精细
读多少数据
```

## 为什么我的理解发生了变化

上一篇 DSA 让我理解了：

> 稀疏必须考虑真实硬件。

而 SATIN 又让我继续往前理解：

> **不同优化手段不一定要分别设计，也可以围绕同一个控制变量统一起来。**

因此我开始把边缘 AI 中的优化理解成：

```text
算法
+
编译器
+
指令集
+
硬件
+
内存系统
```

共同工作的系统问题。

# 我现在认为 SATIN 最值得记住的一点

如果只记一句话，我会记：

> **SATIN 把“剪枝”看成 0 bit，把低精度和高精度放到同一条位宽连续轴上，并用一个统一的重要性信号同时控制 token 稀疏、V 侧精度和 KV Cache 读取深度。**

它解决的不只是：

> Transformer 怎么少算一点？

而是：

> **怎样让计算量、计算精度和数据搬运量都随着 token 的重要程度一起变化。**

# 我还没有完全弄懂的问题

1. SATIN 中精度预算 ε 最终是如何转化成每层、每个 Head 的位宽配置？
2. Q/K 的 partial sum 在什么条件下可以提前确定 token 一定保留或一定剪掉？
3. 误差界为什么会随着处理的 bit plane 增加而不断收紧？
4. V 侧具体怎样根据 softmax 权重分配位宽？
5. KV Cache 的 bit-plane 存储在真实硬件中是怎样组织的？
6. SATIN 自定义的 RISC-V 指令具体各自完成什么功能？
