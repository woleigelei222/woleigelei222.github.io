# 今天读了什么？

今天继续深入阅读论文 **《EdgeAutoOffloadAI: a deep reinforcement learning framework for adaptive task offloading and resource management in mobile edge computing》**。

相比之前主要关注边缘计算中的存储、缓存、聚合和完整性，这篇论文让我开始进入一个更具体的问题：

> 在动态的移动边缘计算（MEC）环境中，任务究竟应该在哪里执行？应该卸载多少？边缘服务器应该分配多少 CPU？无线链路又应该分配多少空口资源？

这类问题看起来只是“任务卸载”，但真正放进实际系统以后，会同时受到网络状态、设备能力、用户行为、服务器负载和资源竞争等因素影响。

因此，真正困难的并不是“要不要卸载”，而是：

> **如何在动态环境里持续做出细粒度、可扩展且相对稳定的联合决策。**

# 三类常见方法及其局限

今天我首先梳理了 MEC 任务卸载中常见的三类方法。

## 1. 静态启发式或基于规则的方法

这类方法计算开销低，规则明确，实现起来也比较直接。

但问题是：

> 规则本身通常不能随着网络状态实时改变。

因此，当信道、服务器负载或任务需求发生变化时，原本有效的规则可能很快偏离较优方案。

## 2. 传统优化方法

例如：

- 线性规划；
- 博弈论；
- 其他基于数学模型的优化方法。

这类方法通常具有更明确的数学结构和性能保证。

但它们往往依赖较精确的系统模型，而且系统规模变大以后，求解复杂度可能迅速增加。

## 3. 强化学习方法

强化学习可以通过与环境持续交互来学习策略，因此更适合动态 MEC 环境。

这也是我今天开始重点理解的方向。

# 为什么早期 DQN 仍然不够？

早期 DQN 已经可以根据系统状态做自适应卸载决策，但它通常需要把动作空间离散化。

例如，假设 CPU 分配比例原本是一个连续变量：

```text
0% ~ 100%
```

如果只粗略划分成：

```text
0%
25%
50%
75%
100%
```

动作数量不多，但控制精度会比较低。

如果为了提高精度，把区间划分得非常细：

```text
0%
1%
2%
...
99%
100%
```

虽然精度提高了，但动作数量会迅速增加，学习难度和计算负担也会变大。

因此，我现在更能理解为什么 DQN 更适合离散动作，而对于 CPU 分配比例、空口时间份额、DVFS 频率等连续控制变量并不理想。

# 固定维度网络难以表达复杂 MEC 关系

MEC 系统并不是简单的一串固定向量。

在真实环境中，可能同时存在：

```text
多个用户
+
多个边缘服务器
+
不同任务
+
不同网络状态
+
不同资源竞争关系
```

一个用户获得更多 CPU，就可能意味着其他用户获得的资源减少；一个边缘服务器拥塞，也会改变多个用户的卸载选择。

因此，我开始把 MEC 看成一个具有明显“实体之间相互作用”的系统。

普通固定维度网络虽然可以输入状态向量，但当用户数量、边缘节点数量发生变化时，扩展会变得困难。

这也是这篇论文引入 Transformer 的重要原因之一。

# EdgeAutoOffloadAI 的核心思路

论文提出的核心框架，是把：

> **PPO + Transformer**

结合起来，用于同时完成任务卸载和资源分配。

我目前把它理解成：

```text
MEC 环境状态
↓
Transformer
负责建模用户、边缘节点和网络状态之间的关系
↓
PPO
根据编码后的状态做策略决策
↓
输出卸载与资源分配动作
```

其中，决策不再只是：

```text
本地执行 / 边缘执行
```

而是进一步涉及：

- 任务在哪里执行；
- 卸载多少；
- 边缘服务器分配多少 CPU；
- 无线链路分配多少空口资源；
- 本地计算资源如何调整。

这让我意识到：

> 真正的 MEC 优化往往不是单一决策，而是多个互相关联的连续与离散变量共同优化。

# 为什么使用 PPO？

PPO（Proximal Policy Optimization，近端策略优化）的一个核心思想，是限制每次策略更新的幅度。

我目前把它理解成：

> 策略要不断改进，但不能一次改得太猛。

如果每次训练后策略变化过大，可能导致学习过程不稳定。

PPO通过限制策略更新幅度，让训练过程更加平稳。

对这篇论文来说，PPO还有另一个重要意义：

> 它比传统 DQN 更适合处理连续、细粒度的资源控制问题。

# Transformer 在这里到底做什么？

今天我对 Transformer 的理解也更具体了一些。

以前我更容易把 Transformer 和自然语言处理联系起来，但在这篇论文里，它的核心价值并不是“处理文本”，而是：

> **建模不同用户、边缘服务器和网络状态之间的复杂关系。**

例如：

```text
UE1 的任务很紧急
Edge1 当前负载很高
Edge2 比较空闲
UE2 也在竞争 Edge2 的资源
```

这时系统不能只单独观察 UE1。

它还需要理解：

```text
UE1 ↔ Edge1
UE1 ↔ Edge2
UE1 ↔ UE2
```

这些关系。

Transformer 的注意力机制可以帮助模型学习哪些实体之间的关系更加重要。

因此我现在可以用一句很简单的话理解这篇论文中的分工：

> **Transformer 负责“看懂当前局势”，PPO 负责“根据局势做决定”。**

# Jain 公平指数：不能只让条件好的用户一直占资源

论文还引入了 Jain 公平指数，用来衡量多用户之间的资源分配是否均衡。

公式为：

\[
F(t)=\frac{\left[\sum_{u=1}^{U}x_u(t)\right]^2}
{U\sum_{u=1}^{U}x_u(t)^2}
\]

这个指标让我意识到，在多用户 MEC 系统中，仅仅追求“总时延最低”可能并不够。

如果算法一直把资源分给信道条件最好、任务最容易完成的用户，那么整体平均性能可能很好，但某些用户可能长期得不到足够资源。

也就是出现：

> **用户饥饿（starvation）**

因此，公平性是另一个必须被考虑的目标。

# CVaR：平均时延低，不代表极端情况也安全

论文还在奖励函数中加入了 CVaR，用于关注尾部风险。

我现在对 CVaR 的理解是：

> 它不是只看平均时延，而是重点关注最差的那一批极端高时延任务。

如果一个系统平均时延很好，但偶尔出现特别高的延迟，那么对于自动驾驶、工业控制等时间敏感任务来说仍然可能不可接受。

因此：

```text
平均时延
→ 看系统整体通常表现如何

CVaR
→ 看最坏的一批情况到底有多糟
```

这让我进一步理解了一个问题：

> 一个系统“平均表现好”与“系统足够可靠”并不是完全相同的概念。

# 论文中的主要优化点

我把论文的主要贡献整理成四点：

1. 使用 PPO 与 Transformer 组成混合 DRL 架构，使任务卸载和资源控制更加连续、细粒度且具有扩展能力；
2. 加入公平性优化，降低异构用户之间长期资源分配不均的问题；
3. 在奖励中加入 CVaR 尾部风险建模，关注平均时延之外的极端延迟；
4. 使用 NS-3 仿真，与 Greedy Min-Latency、DQN、RA-PPO 等方法进行比较，并从时延、能耗、公平性、deadline 违约和扩展性等角度进行评价。

# 一个值得补充的强化学习基础

今天还重新整理了一下 MDP 的基本形式：

\[
(S,A,P,r,\gamma)
\]

其中：

- \(S\)：状态空间；
- \(A\)：动作空间；
- \(P\)：状态转移概率；
- \(r\)：奖励函数；
- \(\gamma\)：折扣因子。

放到 MEC 任务卸载问题里，我目前可以简单理解成：

```text
State
→ 当前任务、信道、服务器负载等状态

Action
→ 卸载位置、卸载比例、CPU资源、空口资源等决策

Reward
→ 根据时延、能耗、公平性和风险给出反馈
```

然后智能体不断通过：

```text
状态
→ 动作
→ 环境变化
→ 奖励
→ 新状态
```

去学习更合适的策略。

# Transformer 不是“没有代价”的

论文还对 MLP 和 Transformer 做了对比。

在相同硬件条件下，Transformer 会带来约 20%～30% 的额外训练时间。

但从样本数量来看，两者的收敛速度并没有出现同等级别差异。

这说明我现在更愿意把 Transformer 的主要收益理解成：

> **提高状态表示和最终决策质量，而不是单纯减少训练样本数量。**

也就是说，Transformer 并不是“免费获得更好性能”。

它用更多计算开销，换来了对复杂用户—边缘节点关系更好的建模能力。

# 今天看到的几个核心权衡

我觉得这篇论文目前最值得学习的，不只是 PPO 或 Transformer 本身，而是它体现出来的各种权衡。

## 1. 时延与能耗

积极卸载：

```text
可能减少本地计算时延
↓
但信道不好时
↓
无线传输能耗可能增加
```

而选择本地执行：

```text
可能减少无线传输
↓
但本地设备算力有限
↓
任务时延可能增加
```

## 2. 公平性与平均性能

如果只追求平均时延：

```text
系统可能优先服务“条件好的用户”
```

加入公平性以后：

```text
资源会分给更多用户
↓
长期服务更均衡
↓
但平均时延可能轻微上升
```

## 3. 模型能力与计算成本

```text
Transformer
→ 关系建模能力更强
→ 扩展性更好
→ 但训练和推理成本更高
```

所以这个框架仍然不可能适合所有 MEC 场景。

# 今天最重要的理解

## 我原本以为

我之前更容易把任务卸载理解成：

> 判断任务是在本地执行还是发送到边缘服务器。

## 现在我的理解是

现在我发现，真实 MEC 系统中的任务卸载其实是一个联合资源管理问题。

系统可能需要同时决定：

```text
任务执行位置
+
卸载比例
+
CPU分配
+
空口资源
+
本地计算频率
```

而且这些决策还要同时考虑：

```text
时延
能耗
公平性
deadline
极端风险
```

所以真正困难的是：

> **在不断变化的环境中，动态寻找多个目标之间可以接受的平衡。**

## 为什么我的理解发生了变化

因为这篇论文没有把“任务卸载”单独拿出来优化，而是把它和 CPU、无线资源、公平性、极端时延风险一起考虑。

这让我第一次比较明确地感受到：

> 边缘计算中的优化问题往往不是“把一个指标做到最低”，而是在多个互相冲突的目标之间持续做决策。

# 我现在最感兴趣的问题

读完今天这一部分后，我产生了一个很具体的问题：

> **既然 Transformer 可以提升复杂 MEC 环境下的状态建模能力，但又会增加训练和推理成本，那么能不能设计一种更轻量化的 Transformer，使它保留用户—边缘节点关系建模能力的同时，降低计算开销？**

这个问题我目前还没有答案。

但相比前面只学习“Transformer 为什么有用”，我觉得这个问题已经开始接近：

> **现有方法还有什么地方可以继续改？**
