# 从缓存复用到 NVMe 直通：MTDS 与 DUAL-BLADE 学习记录

## 今天的学习主线

今天继续回顾之前读过的论文，重点是 **MTDS** 和 **DUAL-BLADE**。与早期关注 Attention 计算量的论文不同，这两篇都从 KV Cache 的存储与数据移动出发，但切入点不同：**MTDS 解决缓存值不值得复用、应该保存或淘汰哪些数据；DUAL-BLADE 解决需要访问 SSD 时，怎样减少 I/O 路径开销并隐藏传输等待。**

## 一、MTDS：缓存命中并不意味着一定应该加载

LLM 推理包括 Prefill 和 Decode 两个阶段。Prefill 处理输入序列并产生历史 KV；Decode 每生成一个新 token，通常需要利用历史 KV 参与 Attention。随着上下文变长，保存这些 KV 的存储压力越来越大。

MTDS 使用 **GPU 显存—CPU DRAM—SSD** 的分层存储思路扩展可用容量。但低层存储虽然容量大，传输到 GPU 仍有成本。因此，作者提出的关键问题是：如果已有缓存位于 DRAM 或 SSD，**直接加载旧 KV 是否真的比重新计算更快？**

可以用下面的简化判断帮助理解：

\[
T_{\mathrm{load}}<T_{\mathrm{recompute}}
\]

只有在加载成本更低、且满足缓存复用条件时，复用才能更有利。这个表达式是我的学习归纳，不代表论文所有策略只依据两个数值作决定。

### 1.1 选择性 KV 加载器

论文将它组织成三个模块：

1. **Request Metadata Module**：收集请求公共前缀、可复用 KV、缓存位置及相关成本信息。
2. **Policy Analysis Module**：比较复用与重新计算的代价，选择 Full Load、Partial Load 或 No Load。
3. **Policy Execution Module**：落实所选策略，完成必要的数据加载与未命中部分的计算。

我对这里的最大收获是：**缓存命中率只是一个指标，真正要优化的是请求完成时间和资源成本。**

### 1.2 卸载调度器

加载关注的是“旧 KV 要不要取回来”，卸载关注的是“新 KV 应该先保存哪一份”。如果按照任务完成顺序直接写回，可能导致将来很可能重用的缓存没有及时保存，而价值较低的数据却占用了 DRAM。

MTDS 使用历史请求的前缀匹配情况估计未来复用机会，对卸载进行优先级安排，并尽量减少重复、无效的数据搬运。需要强调：**历史匹配只能反映可能的复用趋势，不能提前准确知道未来请求。**

### 1.3 自适应淘汰

当 DRAM 逐渐接近容量上限时，需要判断哪些缓存优先淘汰。传统 LRU 主要依据最近一次使用时间，而论文还考虑历史利用程度与近期请求前缀匹配情况。

学习记录中用下式概括这类融合思路：

\[
U_{\mathrm{final}}=(1-\xi)h+\xi m
\]

其中，\(h\) 是历史利用指标，\(m\) 是近期匹配比例，\(\xi\) 是两者的权重。比如取 \(h=0.1,m=0.4,\xi=0.25\)，得到 \(U_{\mathrm{final}}=0.175\)。**这组数值仅是教学手算，不是我运行的实验。**

此外，系统会结合 DRAM 占用量设置不同淘汰阈值：压力较小时谨慎淘汰，空间紧张时更积极地移除低价值缓存。

## 二、DUAL-BLADE：为什么 SSD 容量足够，读取还是可能很慢？

学习 MTDS 后，我进一步阅读 DUAL-BLADE。它让我意识到：**SSD 的性能不只取决于设备标称带宽，还取决于数据实际经过的 I/O 路径。**

### 2.1 Page Cache Thrashing：反复换入换出的代价

Linux Page Cache 可以在 DRAM 中缓存文件数据。如果需要反复访问的 KV 工作集超过可用 Page Cache 容量，刚读入的缓存可能很快被淘汰，而下一轮又需要从 SSD 读取，产生重复 I/O。

```text
读取 A → 读取 B → 读取 C
内存压力导致 A 被淘汰
下一轮再读 A → 又需要访问 SSD
```

这不是说 Page Cache 一定低效，而是说明它的收益受到容量和访问模式约束。

### 2.2 双路径 KV 驻留

DUAL-BLADE 让一部分层的 KV 走 Page Cache，剩余部分走 **NVMe-direct**，避免所有 KV 都争抢有限的页缓存空间。

原始记录中的手算例子是：模型有 12 层，每层 K 占 100 MB、V 占 100 MB，Page Cache 预算 \(X=600\) MB，则每层 KV 共需 200 MB，可容纳：

\[
n_1=\left\lfloor\frac{600}{2\times100}\right\rfloor=3
\]

所以在这一教学条件下，前 3 层可以走 Page Cache，其余 9 层走 NVMe-direct。这里的分组是**按预算进行的路径安排**，不是依据某个 token 的语义重要性。

### 2.3 NVMe-direct 与 LBA

在论文讨论的传统写入路径中，数据可能经过：

```text
GPU → Host Pinned Memory → Page Cache → SSD
```

而 NVMe-direct 尝试使用：

```text
GPU → Host Pinned Memory → NVMe SSD
```

它绕开常规 Page Cache 中转，减少部分内存复制及软件 I/O 路径成本；但**并不是 GPU 与 SSD 之间完全不经主机缓冲区的点对点直连**。

论文还使用 **LBA（逻辑块地址）**组织顺序、可定位的存储访问。这里要明确：**连续 LBA 是逻辑地址连续，不意味着 SSD 内部 NAND 的物理地址必然连续。**

### 2.4 自适应流水线

即使 SSD 读取路径更快，GPU 仍可能在等待 KV 到达时闲置。论文比较两种并行策略：

- **Overlap-Intra**：并发执行同类 SSD I/O 操作，例如两个线程分别读取 K、V。
- **Overlap-Cross**：交错安排 SSD 读取与主机到 GPU 的 DMA，让不同硬件阶段尽量重叠。

作者根据运行初期的实际表现选择策略，而不是规定所有设备都使用一种固定重叠方式。这里我的理解发生了变化：**SSD 很忙并不一定代表整个推理流水线效率高；真正要优化的是 SSD I/O、内存缓冲与 GPU DMA 之间的等待关系。**

## 三、阶段性理解：两篇论文解决的是不同层次的问题

| 论文 | 我今天抓住的核心问题 | 优化对象 |
|---|---|---|
| MTDS | KV 值不值得加载、保存与淘汰？ | 分层缓存管理与复用决策 |
| DUAL-BLADE | 已经需要访问 SSD，怎样少中转、少等待？ | I/O 路径和流水线调度 |

如果用一句话区分：**MTDS 关注“该不该搬”，DUAL-BLADE 关注“怎么搬得更合理”。** 这个联系是我对两篇论文的整理，并不表示它们的实现可以直接拼接。
